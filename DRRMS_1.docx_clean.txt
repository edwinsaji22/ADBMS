Self-created dataset will be used to complete database design, populated and tested using the concepts covered in the ADBMS practical. 

Objectives 

1. To enable the design of a structured dataset using proper data modelling techniques. 

2. To develop practical skills in SQL for database creation, manipulation and querying. 

3. To enhance analytical thinking through multi-phase database development. 

Phase 1 - Data Modelling and Dataset Design 

1. Dataset: A small DRRMS dataset containing disaster events, shelters, donors, resources, requests, volunteers and distribution records. The same data will be used in all later phases. 

2. Entity and attribute identification: DISASTER_EVENT, SHELTER, DONOR, RESOURCE, REQUEST, VOLUNTEER and DISTRIBUTION as the main entities, with attributes required to store their respective details. 

3. ER modelling: DISASTER_EVENT-SHELTER, DONOR-RESOURCE, SHELTER-RESOURCE, SHELTER-REQUEST, RESOURCE-DISTRIBUTION and VOLUNTEER-DISTRIBUTION will be modelled mainly as 1:M relationships. 

4. Relational schema: Convert the ER model into tables. Primary keys will identify records and foreign keys will connect related tables. 

5. Normalization: donor, shelter, request and distribution details will be stored separately so that repeated data is reduced and the schema remains in 3NF. ER Diagram

Phase 2 - Database Creation and Data Preparation 

1. DDL: Create DRRMS_DB and all seven tables using CREATE DATABASE and CREATE TABLE. PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL and CHECK constraints will be defined with the tables. 

2. DML: Enter sample data using INSERT. UPDATE will be used when request status or resource quantity changes, while DELETE will be tested only where foreign-key relations are not affected.

3. Data cleaning and constraints: duplicate donor emails and shelter locations will be prevented, required IDs will not be NULL, and invalid negative quantity or capacity values will be restricted. 

4. NULL handling: fulfilled_date will stay NULL while a request is pending and remarks can stay NULL when there is no comment. IS NULL / IS NOT NULL will be used to find such records. 

5. Basic queries: SELECT, WHERE and ORDER BY will be used to display active shelters, pending requests, resources by type, volunteers by skill and distributions by date. 

6. Aggregate functions: COUNT() will calculate requests per shelter, AVG() will calculate average resource quantity per type and SUM() will calculate total resources distributed. 

Phase 3 - Data Querying and Analytical Operations 

1. Joins: join DONOR + RESOURCE for donation details, SHELTER + REQUEST + DISASTER_EVENT for relief reports, and RESOURCE + DISTRIBUTION for allocation history. 

2. Nested queries and subqueries: find shelters whose request count is above the average request count and resources whose distributed quantity is above the overall average. 

3. View: create Shelter_Resource_Summary to display shelter name, disaster event, resource type, quantity and distributed quantity through one reusable query. 

4. Query execution and optimization: use EXPLAIN on the shelter-request-event join. Indexes will be created on frequently searched columns such as RESOURCE.shelter_id, REQUEST.shelter_id and DISTRIBUTION.resource_id and the query plan will be checked again. 

5. Function: create GetShelterRequestCount(shelter_id). It will receive a shelter ID, count the matching records in REQUEST and return the total requests raised by that shelter. 

6. Procedure: create AddDistribution(resource_id, volunteer_id, distributed_qty). It will accept the distribution details, insert a new DISTRIBUTION record and reduce the available quantity in RESOURCE. Phase 4 - Data Integrity and Transaction Handling 

1. Transaction handling: when I allocate a resource to a distribution, I will start one transaction, insert the DISTRIBUTION record and reduce RESOURCE.quantity. A SAVEPOINT will be used before the final update. COMMIT will be used if both operations succeed and ROLLBACK if an error occurs. 

2. Atomicity: the distribution insertion and resource-quantity update will be treated as one unit. If either operation fails, the complete transaction will be rolled back so the database does not remain partly updated. 

3. Concurrency case: before confirming a distribution I will check that the selected resource still has sufficient quantity inside the transaction. This will help prevent the same resource from being over-allocated to two distributions at the same time. 

4. Integrity constraints: foreign keys will ensure that SHELTER uses an existing DISASTER_EVENT, RESOURCE uses an existing DONOR and SHELTER, REQUEST uses an existing SHELTER, and DISTRIBUTION uses an existing RESOURCE and VOLUNTEER. 

5. Final validation: check for missing references, confirm that fulfilled requests match distributed quantities, and run the basic queries, joins, subqueries, view, function, procedure and transaction cases to verify the database. Outcome of the Project 

1. A normalized relational database for disaster relief resource records up to 3NF. 

2. Practical implementation of DDL, DML, constraints, basic queries, aggregates, joins, subqueries, views, functions/procedures and transactions. 

3. Disaster event, shelter, donation, request and distribution information can be stored and retrieved through related tables. 

4. The project will give hands-on understanding of data modelling, SQL querying, integrity and transaction handling using one complete database case study.
